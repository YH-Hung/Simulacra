# Simulacra M3 Phase 7 — Go SDK (`simulacratest`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `github.com/yinghanhung/simulacra/simulacratest` — a `testing.T`-integrated Go SDK that boots an in-process server, registers schemas, creates stubs from typed messages, verifies calls, and captures requests, all through the admin API — plus the `respond.literal` stub-grammar field it depends on.

**Architecture:** One new package in the core module. `Client` wraps the five generated connect clients against any admin address; `Server` embeds a `Client` and owns an in-process `server.Server`. Builders render one stub document as JSON and send it with `CreateStub`; a client-local, copy-on-write type registry resolves types the test registered at run time. One additive field in `internal/stub` (`respond.literal`) makes typed responses immune to template re-interpretation; committed generated code for `testdata/protos/shop/v1` makes the typed paths testable.

**Tech Stack:** Go 1.25.0, module `github.com/yinghanhung/simulacra`. Direct dependencies already present and sufficient: `connectrpc.com/connect` v1.20.0, `google.golang.org/grpc` v1.82.0, `google.golang.org/protobuf` v1.36.11, `google.golang.org/genproto/googleapis/rpc`, `gopkg.in/yaml.v3` v3.0.1, `github.com/bufbuild/protocompile` v0.14.1. Tools module gains `google.golang.org/grpc/cmd/protoc-gen-go-grpc` **v1.6.2**. buf 1.72.0 (pinned in `tools/`).

**Spec:** `docs/superpowers/specs/2026-10-04-m3-p7-go-sdk-design.md`, cited as "spec §N". Approved at `b996b74`. Phase 6 is complete at `aa064ed`.

## Global Constraints

- **Core `go.mod` and `go.sum` do not change.** `tools/go.mod` gains exactly one tool: `google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.6.2`.
- **No changes to `api/` or `gen/`.** This phase adds no RPC.
- **Files touched outside `simulacratest/`:** `internal/stub/stub.go` (the `literal` field only, Task 1), new test files in `internal/stub`, `internal/admin`, `internal/schema`; generated `internal/testpb/`; `buf.gen.testdata.yaml`; `Makefile`; `.github/workflows/ci.yml`; `tools/go.mod`, `tools/go.sum`. Nothing else.
- **The SDK reports only through `t.Fatalf` and `t.Errorf`, and every helper calls `t.Helper()` first.** Tests depend on this: the recording double overrides exactly those three methods.
- **Server diagnostics pass through verbatim.** The SDK prefixes `simulacratest: <Op>: ` and appends at most one SDK-sourced line; it never rewords or reclassifies a server message (spec §10, P6's rule).
- **Every admin RPC runs under `context.WithTimeout(context.Background(), c.timeout)`, default 30 seconds. Never `t.Context()`** (spec §3).
- **Method names are accepted as `/pkg.Svc/M` or `pkg.Svc/M`** everywhere a method is taken.
- **Every discriminating test carries a named mutation check** — state the mutation, confirm the test fails under it, revert. Carried from the phase 5 and 6 plans.
- **Run the full suite with `-race -count=1`.**
- **No `time.Sleep` to order anything a test asserts.** Wait on a channel the system under test signals, with a deadline.

## Review Focus

Inputs the spec implies but whose behavior no spec test pins, most likely to bite first. Each has a test in its owning task.

1. **A response type whose JSON form is not an object** (an RPC returning `google.protobuf.Value` holding a number, or a `Timestamp`, wrapper, `ListValue`) — `respond.message` must be a mapping (`internal/stub/stub.go:34`), so `Respond` must refuse with an explanation naming the JSON kind, not leave the user to decode a YAML unmarshal error. → Task 7, `TestRespondRefusesNonObjectJSON`.
2. **Negative zero anywhere in a typed response** — F6: the server's YAML step turns `-0` into `+0`, and `proto.Equal` cannot see it for `Struct`/`Value` numbers. Expected: `Respond` refuses (spec §12: a known limit, not worked around), never delivers a flipped sign. → Task 7, `TestRespondRefusesNegativeZero`.
3. **Header or trailer keys that differ only in case** — the server lowercases keys and *appends* values (`internal/stub/metadata.go:42`), so `Header("X-A",…).Header("x-a",…)` would silently become a two-value key. Expected: refused as a duplicate. → Task 7, `TestHeaderKeysAreCaseInsensitive`.
4. **A typed nil message** (`(*shopv1.GetOrderResponse)(nil)`) passed to `Respond`, `Request`, or `Response` — expected: a clear refusal, never a panic and never a silently empty stub. → Task 7 `TestRespondRejectsNilMessage`, Task 10 `TestCaptureRejectsNilTarget`.
5. **The two method-name forms, and malformed names** — `/shop.v1.OrderService/GetOrder` and `shop.v1.OrderService/GetOrder` must share one cache entry and cause at most one registration; `"bad"` must not panic and must surface the server's own diagnostic. → Task 5, `TestEnsureMethodNameForms`.

## Pre-verified facts

Established by throwaway probes before this plan was written, then deleted. Spec §14 carries the source-derived facts; these are the probe results.

**F1 — no special-casing of well-known types.** A `FileDescriptorSet` built from the Go-linked `timestamp.proto` and `any.proto` registers as `added=[]` against a registry loaded by `AddProtoDir("testdata/protos")`. `RegisterFiles` sends the full closure, well-known files included.

**F2 — fixtures generate from a non-module directory.** `bin/buf generate testdata/protos --template <template>` exits 0 with `buf.yaml` listing only `api`, emits exactly `shop/v1/order.pb.go` and `shop/v1/order_grpc.pb.go` (no well-known types), and `make lint-api` is unaffected. No separate `buf.yaml` is needed.

**F3 — the `M` option keeps the descriptor equivalent.** The generated `File_shop_v1_order_proto` closure registers as `added=[]` against the `AddProtoDir` registry; `NormalizeFileProto` copies compare `proto.Equal`; the embedded `go_package` is `""`. `order.proto` stays byte-unchanged. protoc-gen-go-grpc v1.6.2 emits `OrderService_GetOrder_FullMethodName = "/shop.v1.OrderService/GetOrder"` and `grpc.SupportPackageIsVersion9`.

**F4 — status code names.** For all 16 non-OK codes, `codes.Code.UnmarshalJSON` accepts `"FAILED_PRECONDITION"`-style names and rejects `codes.Code.String()`'s `"FailedPrecondition"`. A quoted number (`"9"`) is rejected.

**F5 — yaml.v3 integers.** JSON `9223372036854775807` and `-9223372036854775808` decode to `int`, `18446744073709551615` to `uint64`, all exact. JSON `-0` decodes to `int` `0`.

**F6 — the YAML step loses exactly one thing: the sign of negative zero.** protojson output nested as a field, pushed through yaml.v3 → `encoding/json` → protojson, round-trips exactly for: int64/uint64/int32/uint32 extremes, `MaxFloat64`, `SmallestNonzeroFloat64`, `1e20`, `1e21`, `0.1`, `2^53+1`, `MaxFloat32`, float32 `0.1`, NaN, +Inf, binary bytes, empty string, a string holding `yes`, U+2028, tab, newline, NUL, `~`, `{{ x }}`, emoji and escapes, nanosecond `Timestamp`, negative `Duration`, null `Value`. **Lost:** `-0` in `DoubleValue` and `FloatValue` (`proto.Equal` false), and in `Struct`/`Value` numbers (`proto.Equal` **true**, deterministic bytes differ). A YAML literal `-0.0` (float form) would survive; protojson emits `-0`. Per spec §12 the SDK refuses rather than respells.

**F7 — descriptor identity** (spec §14, verified during spec review): same-instance extension decoding is visible; a different extendee instance decodes silently invisible and is detectable via `Range`/`ContainingMessage()`; a shared extendee with a different *extension* instance decodes silently invisible and is **not** detectable from the message.
